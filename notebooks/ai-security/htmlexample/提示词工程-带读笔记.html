① 一图看懂：提示词工程方法论地图

带读提示：文章的逻辑不是平铺的，而是“先打地基 → 再给工具 → 最后工程化”。记这张图，你就抓住了全篇骨架。

② 核心认知三件事（地基）

1. 提示词 = 与 AI 对齐的接口

文章开宗明义：AI 能力极强但完全依赖指令。模糊输入 → 泛泛输出；清晰输入 → 精准输出。这和产品经理写需求文档是一回事——需求的歧义，最终都会变成返工。

对比一眼懂：
模糊 ❌：“帮我写篇关于猫的文章。”
清晰 ✅：“以轻松幽默口吻，为养猫新手写 800 字，重点讲如何选第一只猫 + 接猫前三天准备，含三个小标题，结尾附 checklist。”

2. 三消息角色（API 的硬格式）

角色比喻作用
System幕后导演设定身份、规则、知识范围，对话前生效，只设一次全程遵守
User演员搭档你发出的任务/问题
AssistantAI 演员AI 回复；也可预填来引导格式
最被低估的工具是 System Prompt：相当于给 AI 一份“工作手册”。普通用户在第一条消息里说“请扮演……”也能达到类似效果。

3. Token 与上下文窗口

  • Token：AI 处理文本的单位。经验公式：1000 Token ≈ 750 英文词 ≈ 500 中文字。
  • 上下文窗口：一次对话能处理的最大 Token 量，超出会遗忘最早内容。
  • 关键原则：最重要指令放开头或结尾，避免“迷失在中间（Lost in the Middle）”。

③ 四要素框架（万能模板）

文章收尾处提炼的速查表框架，建议背下来——它是后面所有技巧的浓缩版：

要素问自己示例
角色AI 是什么身份？你是一位专业的……
指令具体做什么？请分析 / 总结 / 生成……
背景前提信息是什么？读者是……用途是……
限制格式/长度/边界？不超…字，JSON，不要……
我的点评：这四要素其实是“WHO + WHAT + WHY/CONTEXT + HOW”。写任何提示词前，先在脑子里过一遍这四个问题，覆盖率就已经超过 80% 的随手提问。

③+ 技巧分布：System 端 vs User 端

文章把技巧混着讲，但落到实际，它们分别“住”在不同的消息角色里。System 端管“它是谁、守什么规矩”，User 端管“这次要它做什么、怎么交”。把技巧按载体分布，才知道什么写进系统提示词、什么写在每次提问里。

System 端 · 系统提示词

对话前生效 · 只设一次 · 全程遵守
= 给 AI 的“工作手册 / 技能设定”

  • 角色设定：专业领域 + 行为方式 + 核心立场
  • 规则与行为准则：五段式第③段“行为规则”
  • 防幻觉（规则型）：允许说不知道、严谨研究助手模板、限制只用提供资料
  • 全局输出格式约束：固定字段写进 System 全程生效
  • System 精炼：核心规则控 500 Token，防“迷失在中间”
  • 知识范围边界：声明“只答某某领域”

User 端 · 用户消息

每次任务 · 技巧最密
= 你临时发出的“任务指令”

  • 清晰直接地表达：受众/篇幅/要不要/用途/拆步骤
  • XML 标签分离数据：包裹 article/resume，防注入
  • 精准控制输出格式：描述 JSON、只输出 JSON、模板填空
  • 思维链触发：一步一步思考、<thinking> 标签
  • 少样本学习：消息里给 2–3 个输入→输出示例
  • 元提示：请 AI 生成/改进/诊断提示词
  • 迭代优化：多输入测试、改提示词再测

两者协作的技巧（边界模糊）

技巧System 端负责User 端负责
角色设定System 设定身份与准则或第一条消息“请扮演……”
防幻觉立规则（允许说不知道、严谨模板）提供 <reference> 并写“只根据资料回答”
Token 意识System 精炼、关键指令放头尾长文档先摘要 / 用 RAG 只传相关片段
一句话速记：System 端管“它是谁、守什么规矩”（持久）；User 端管“这次做什么、怎么交”（临时）。你刚才说“System 算 skill”很贴切——系统提示词本质就是给 AI 装一个特定技能与人设，装好即生效。

④ 基础技巧串讲（高频使用）

基础 1. 清晰直接地表达（性价比最高）

这是文章最推荐先掌握的技巧。五种让指令清晰的方法：明确受众与语气、规定输出篇幅、同时给出“要”和“不要”、说明最终用途、把复杂任务拆成步骤。

记住：清晰 ≠ 啰嗦。关键在每个词有意义、无歧义。

基础 2. 为 AI 分配角色

为什么有效？角色能激活 AI 在该领域积累的知识模式（告诉它“从哪个知识库调取、什么风格表达”）。

有效角色三要素：专业领域（什么专家）+ 行为方式（怎么沟通）+ 核心立场（原则偏好）。

你是一位资深的云架构师，在 AWS 上有超过 8 年经验。
风格简洁务实，以数据说话，提建议时总会权衡成本与性能，
并指出潜在风险。

基础 3. 用 XML 标签分离数据与指令

为什么要分离？防止指令与数据混淆导致逻辑混乱，更重要的是防提示词注入攻击。把用户内容、参考资料用语义化标签（如 <article>、<resume_A>）包裹，恶意指令就被隔离在标签内。

最佳实践：标签名要有实际含义（<resume_A> 优于 <text1>）。

基础 4. 精准控制输出格式

三种方法：

  • 直接描述格式：说明字段结构 + “只输出 JSON”。
  • 提供模板填空：给带占位符的 Markdown 模板，让 AI 填。
  • 预填充（进阶）：在 Assistant 消息里先写 ```json\n{，强制后续输出 JSON；或写“以下是分析结果：”跳过客套话。

⑤ 进阶技巧串讲（推理 & 质量）

进阶 5. 让 AI 逐步思考（思维链 CoT）

原理：模型逐词预测，先写推理过程，内容成为结论依据，准确率提升。三种触发方式：用 <thinking> 标签隔离、直接要求“一步一步思考”、先列论据再下结论。

重要陷阱：一定要“先分析再下结论”，否则 AI 会为结论找理由、而非真正推理。

进阶 6. 用示例教会 AI（少样本学习 Few-Shot）

给 2–3 个“输入→输出”例子，AI 就能学会模式。好示例三标准：覆盖典型变体、格式完全统一、质量高于数量（2–3 个精心设计 > 10 个随便凑的）。常与角色+指令+格式组合使用。

进阶 7. 避免 AI 胡说八道（防幻觉）

五种策略：

  1. 允许说“不知道”（System 里写明不确定就直说）；
  2. 限制只使用提供的信息（只根据 <reference> 回答）；
  3. 先找证据再给结论（<evidence> → ）；
  4. 要求标注置信度（高/中/低）；
  5. API 层把 temperature 设为 0。
医疗 / 法律 / 财务等高风险领域：必须提供权威文档，并提示用户自行核实。

⑥ 工程化落地（从“写好一句”到“搭好系统”）

工程 8. 五段式架构（复杂提示词）

把长提示词拆成五段：① 角色与目标 ② 背景知识与数据（XML 包裹）③ 行为规则 ④ 输出格式 ⑤ 示例。文章给了“法律合同审查助手”的完整案例，是这套方法论的集大成示范。

工程 9. 提示词链（Prompt Chaining）

超长提示词容易遗漏、逻辑干扰、难定位错、成本高。把任务拆成子步骤串联：长文档分析（提取→分析→报告）、代码生成（需求→接口→实现→测试）、内容创作（大纲→撰写→润色）。每步间加输出验证逻辑，异常时重试或切换备用提示词。

工程 10. 元提示（Meta-Prompting）& 迭代优化

元提示 = 用提示词生成/改进提示词（从零生成、诊断改进、反向推导）。推荐工作流：元提示生成初稿 → 人工按技巧强化（效率提升 3–5 倍）。

迭代工作流：起草 → 多输入测试 → 分析问题（跑题/格式/推理/虚假）→ 修改 → 再测试。记得做版本管理（v1.0 / v1.1 / v2.0 + 日志）。

⑦ 我的点评与使用建议

这篇文章的价值在于它把零散的“调参经验”讲成了体系，而且同时照顾了普通用户和开发者两条线。我的几点补充建议：

  • 普通用户：先吃透“四要素 + 清晰表达 + 角色设定”三件套，日常 90% 场景够用。少样本和思维链等用到时再取。
  • 开发者：重点看五段式、提示词链、防幻觉的 System Prompt 模板——这些直接决定 AI 应用的稳定性与成本。
  • 别神化元提示：文章也提醒了，AI 缺业务背景，生成的提示词必须人工按技巧强化并实测，不能盲目信任。
  • 建立自己的“提示词工具箱”：把邮件润色、周报、调试等高频有效提示词存起来，这是最实在的生产力资产。
一个行动建议：拿你最近写得最烂的一条提示词，按四要素（角色/指令/背景/限制）改写一遍，对比输出——这是最快的建立“手感”的办法。
